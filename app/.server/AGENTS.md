# AGENTS.md: app/.server

Server-only code. Nothing in this folder may be imported by code that ends up in the browser bundle. Import it only from route `loader`/`action` functions or from other `.server` modules.

## Environment: `env.ts`

- Read configuration only through `getEnv()`, never through `process.env` directly. `getEnv()` loads `.env` (existing variables win), validates with zod and memoizes the result.
- To add a variable, extend `envSchema`, add it to `.env.example` and the README table, and add a case to `env.test.ts`.
- The database URL is `JASSMINDB_URI` (injected by Aspire for the `jassmindb` resource) when it's set, otherwise `DATABASE_URL`. Aspire's value must win, because `.env` usually keeps a `DATABASE_URL` for runs without Aspire. Keep this precedence in `env.ts` and `drizzle.config.ts`.
- `SMTP_URL` (optional, `smtp://` / `smtps://`) is where contact and order emails go; under Aspire it's the `smtp4dev` container's SMTP endpoint. `CONTACT_INBOX` and `CONTACT_FROM` have defaults, and `ORDER_FROM` (order emails' sender) falls back to `CONTACT_FROM`. The mail variables have their own schema: `parseMailEnv(source)` validates only them, for `pnpm db:send-order-emails`, which runs without the web app's env.
- `STRAPI_URL` defaults to `http://localhost:1337` and falls back to `CMS_HTTP` (Aspire's `cms` reference). `STRAPI_API_TOKEN` is optional on purpose, so the app boots before a Strapi admin has created the token.
- CMS sync (#40): `CMS_SYNC_SECRET` (32+ characters, optional) authenticates Strapi on the `/cms/*` routes, and `STRAPI_SYNC_TOKEN` (optional) is the Strapi token that writes products and orders. Their own schema, `parseCmsSyncEnv(source)` (with `STRAPI_URL`), serves `pnpm db:sync-cms`, which runs without the web app's env.

## CMS: `cms/`

Editorial content (blog, home page copy, contact details, special offers) lives in Strapi (`cms/` at the repo root). Products, orders and users stay in PostgreSQL, but staff edit products and orders in the Strapi admin, which writes through to PostgreSQL (see CMS sync below).

- Loaders read CMS content only through `cms/content.ts` (`getHomePage`, `getSiteSettings`, `listBlogPosts`, `getBlogPostBySlug`, `listActiveOffers`). These return the DTOs from `~/lib/cms`, never raw Strapi shapes, with media URLs already absolute.
- CMS content is localized (`uk` default, `en`; #43). Every content query takes a `Locale`: pass `await getLocale(request)` from the loader. When the requested locale has no entry, it falls back to Ukrainian through `withLocaleFallback` (a single type's 404 counts as missing; other errors never fall back), and each DTO's `locale` says which language was served. Components mark fallback text with `lang={useContentLang(dto.locale)}`. The blog list paginates over the Ukrainian posts and swaps in their translations by `documentId`; `listActiveOffers` does the same for the offers whose window includes `now`.
- `cms/client.ts` (`cmsFetch`) always adds `status=published` (plus `locale` when given), sends the read-only token and times out after `CMS_TIMEOUT_MS`. Every response is validated with a schema from `cms/schemas.ts`. When you add a field in Strapi, add it to the schema, the DTO, the mapper and the fixtures. `site-setting.legalName` (optional, not localized) names the ФОП who controls personal data on `/privacy`, which renders without the CMS block instead of failing when Strapi is down.
- CMS images (#80): every image slot `<name>` has three Strapi fields, so staff upload a photo once but can still give one language its own picture and alt text:
  - `<name>`: the shared image (media, `i18n.localized: false`; Strapi copies it to every locale).
  - `<name>Localized`: this language's image, which replaces the shared one (media, `localized: true`).
  - `<name>Alt`: this language's alt text (`string`, max 200, `localized: true`). It describes whichever image is shown; when blank, the file's own `alternativeText` is used.

  Map a slot only with `pickImage({ shared, localized, alt }, baseUrl)` in `cms/content.ts` (override, else shared, else `null`), populate both media fields, and keep a single `image` / `coverImage` in the DTO. Strapi can't share a field inside a localized component, so on the home page the shared images are top-level (`heroImage`, `aboutImage`) while the override and alt live in the component (`hero.imageLocalized`, `hero.imageAlt`, `about.…`). Offers use `image`, blog posts `coverImage`. New image fields follow the same convention and get their admin hints in `IMAGE_FIELD_HINTS` (`cms/src/index.ts`). Product images aren't localized (#40). The data migration that moved the old per-locale home page photos is `cms/database/migrations/2026.11.01T00.00.00.shared-home-images.js`.
- Failures throw `CmsError` (`cms/errors.ts`). In loaders, wrap CMS calls with `.catch(cmsUnavailable)`, which turns them into a 503 for the `ErrorBoundary`. A missing blog post is `null`, so throw a 404 for it in the route.
- Social links (#101): `toSiteSettings` cleans them with `normalizeSocialLinks` (`~/lib/social`): only `https:` URLs, tracking parameters (`xtok`, `igsh`, `utm_*`, …) removed, ordered Instagram, Telegram, then the rest. The `_shop` layout reads them for the footer and mobile menu through `cms/social.ts` (`getSocialLinks`), the one cached CMS read: 60 s per locale, shared in-flight reads, and it never throws (the last links or `[]` while Strapi is down), so it can't slow down or fail a page. Don't use `cmsUnavailable` there.
- Offers (#55) are editorial and never change prices themselves: `priceNote` is text. A price an offer advertises comes from a discount rule in PostgreSQL (#59, see Discounts below), e.g. the tester trio's `priceNote` matches the `tester-trio` rule; keep the two in sync. `startsAt`/`endsAt` are offset date-times compared as instants (`isOfferActive`: start inclusive, end exclusive), and `compareOffers` (`sortOrder`, then latest start) decides the order and the hero. Offers reference shop products by `public_id`; `getProductSummaries` resolves them in one query and drops unknown or unsold ones.
- Tests use the recorded Strapi responses in `cms/__fixtures__/`: `<name>.json` is the `uk` response and `<name>.en.json` the `en` one. Re-record both from a seeded Strapi (`pnpm cms:seed`) when the content model changes.

## Markdown, mail and rate limiting

- `markdown.ts`: `renderMarkdown()` turns CMS Markdown into sanitized HTML (render it with `RichText` from `~/components/ui/RichText`); `toPlainText()` is for meta descriptions. Never inject CMS HTML that didn't go through `renderMarkdown()`.
- `mail.ts`: `getMailTransport()` returns the shared nodemailer transport built from `SMTP_URL`, or `null` when it's not set. Send plain-text emails and keep user input out of headers with `stripLineBreaks`. Services take a `MailSender` (the `sendMail` part of a transport), so tests pass a fake.
- `rate-limit.ts` (#143): fixed-window `createRateLimiter({ name, limit, windowMs, store })`, async (`isBlocked` / `hit` / `reset` return promises: always `await` them). The app's limiters use `appRateLimitStore`, the `rate_limits` table (`db/queries/rate-limits.ts`: one atomic upsert per hit), so counters survive restarts and are shared by every instance. Keys are stored as `<name>:<sha256 of the key>`, never as emails or IPs. `createMemoryRateLimitStore()` is only for `/csp-report` (a report flood mustn't become writes) and tests; `vitest.setup.ts` puts the app limiters on a fresh memory store for every test file (`setAppRateLimitStore`), so tests never write to the development database. `pnpm db:prune-rate-limits` deletes ended windows.
- `client-ip.ts` (#143): `getClientIp(request)` (re-exported by `rate-limit.ts`) is the `X-Forwarded-For` entry `TRUSTED_PROXY_HOPS` places from the right, or `undefined` with 0 hops (`react-router-serve` gives no socket address). Never read `X-Forwarded-For` yourself. Tests run with `TRUSTED_PROXY_HOPS=1` (`vitest.config.ts`), so route tests can send `X-Forwarded-For` to stand for different clients.
- `security-headers.ts` (#143): the root's first middleware sets the security headers on every response and, on HTML, the nonce-based CSP (`CSP_MODE`: `report-only` or `enforce`). Give every new inline `<script>` `nonce={useNonce()}` (`~/lib/nonce`); never add `'unsafe-inline'` to `script-src`. A new external origin goes in `buildCsp`. `csp-report.ts` parses and logs the reports `/csp-report` receives. See `docs/security.md`.
- `services/contact.ts`: the home page contact form (honeypot → rate limit → email to `CONTACT_INBOX`). Dependencies are injectable for tests.
- `services/order-email.ts` (#45): `buildOrderConfirmationEmail` renders the plain-text confirmation from the stored order (`findOrderConfirmation`) in the row's locale, and `buildGiftCardEmail` / `buildGiftCardRecipientEmail` a paid gift card's code (#125, see Gift cards below); `deliverOrderEmails({ orderId? })` claims due `order_emails` rows, sends them and marks them `sent`, or keeps the error for a retry. It never rejects. Its queue functions come from `orderEmailDeps(db, mailer, env)`, injectable for tests. It must not import `db/index.ts` (the app pool validates the web app's whole env, which the retry job doesn't have); the app's wiring is `deliverOrderConfirmation(orderId)` in `services/orders.ts`.

## Database: `db/`

- `db/index.ts` exports the single Drizzle client `db` (with `casing: "snake_case"`) and the `Db` type. Don't create other pools in app code. `db/client.ts` (`createDb(url)`) is only for CLI scripts (`db/scripts/`) and integration tests, which connect without `getEnv()` and close their own pool.
- Define tables and enums in `db/schema.ts`, in TypeScript camelCase. The `snake_case` casing maps them to snake_case columns. drizzle-kit doesn't apply the casing to auto-generated constraint names, so give `.unique()` and similar constraints an explicit snake_case name (e.g. `products_public_id_unique`).
- Build enums from the value arrays in `~/lib/enums` (`pgEnum("gender_type", GENDERS)`), so the TS unions and the database can't drift apart.
- `products.price` is `numeric(10, 2)` and comes back as a string, so never use floats for money. `volume_ml` is the volume of one unit, and the total is `pack_size * volume_ml`. `public_id` (UUID v7 from `uuidv7()`, PostgreSQL 18+) is the stable external key, while `id` stays the FK target.
- Products are sold in volume variants (`product_variants`, #26): one row per size with its own `price` (`numeric(10, 2)`), `stock_quantity`, `track_stock` and `volume_ml`. The CHECK limits `volume_ml` to `PERFUME_VOLUMES_ML` from `~/lib/enums`, `(product_id, volume_ml)` is unique, and `pack_size` stays on the product. A variant's `public_id` is what forms post as `variantId`. Products without variants aren't listed in the catalog.
- `products.price`, `products.volume_ml` and `products.stock_quantity` are **deprecated** (still NOT NULL, kept until after #16): app code reads price, volume and stock only from `product_variants`. New products still have to fill them, e.g. with their main size.
- Cart lines are per variant: `cart_items.variant_id` is required, and `(cart_id, variant_id)` is unique. Keep `cart_items.product_id` equal to the variant's product. Validate a submitted `variantId` with `checkVariantForCart` (`services/products.ts`) before you store it.
- Stock tracking (#98): the shop pours from large bottles, so a size is always available unless `product_variants.track_stock` is on (it defaults to off; migration 0020 turned it off for every existing size). Read stock only through `variantStock` (`db/queries/products.ts`: `stock_quantity` when tracked, else `UNTRACKED_STOCK` = `MAX_LINE_QUANTITY`, so a line can never exceed it) or `availableStock` (the same, but 0 for an archived product). The cart, guest-cart merge and the checkout check then need no special case. Writes are explicit: `decrementVariantStock` and `restockOrder` only touch tracked sizes, and only their products are queued for Strapi. `ProductVariant.trackStock` tells the UI not to show "only N left" for the stand-in number. `stock_quantity` and its CHECK stay, for sizes that track stock again (e.g. a limited edition).
- At checkout (#11), check and decrement `product_variants.stock_quantity` (tracked sizes only, #98) inside the order transaction, copy the variant price into `order_items.price_at_purchase`, and set `order_items.variant_id` and the `order_items.volume_ml` snapshot.
- Commerce tables (`carts`, `cart_items`, `orders`, `order_items`): every order amount and `order_items.price_at_purchase` is also `numeric(10, 2)`, computed on the server. Their row types (and those of `product_variants` and `discounts`) are mirrored in `~/lib/commerce`, and `schema.test.ts` fails if the two drift apart. `orders.payment_method` is limited to `PAYMENT_METHODS` by a CHECK constraint. `carts.user_id` and `orders.user_id` use `on delete restrict`, so a user with carts or orders can't be deleted. `carts.session_id` references `sessions` with `on delete set null`.
- Analytics tables (`sessions`, `user_events`): these are visitor sessions for traffic and conversion analysis, not the auth cookie session in `session.ts`. Their row types are mirrored in `~/lib/analytics` (`AnalyticsSession`, `UserEvent`) and checked by `schema.test.ts`. `user_events.event_type` is limited to `EVENT_TYPES` by a CHECK constraint, so adding an event type means a migration that rewrites the check. `user_id` is filled in after login and set to `null` when the user is deleted (rows keep `anonymous_id`); deleting a session cascades to its events, and deleting a product nulls `user_events.product_id`. Sessions are created by `getVisitor` and events by `trackEvent` (below). `sessions.ended_at` is the time of the last request in the session (not a close time); `sessions.traffic_source` / `traffic_medium` / `traffic_campaign` say where that visit came from and are copied onto each of its events, while `users.first_touch_*` keep where the person first came from. These are ML features: never drop or rename them.
- Order email outbox (`order_emails`, #45): one row per order (or gift card, #125: `order_id` / `gift_card_id`, exactly one is set, `order_emails_target_check`) and `type` (`ORDER_EMAIL_TYPES`: `confirmation`, `gift_card`, `gift_card_recipient`; unique per target), with the `locale`, `status` (`ORDER_EMAIL_STATUSES`: `pending` → `sent`, or `failed` after `MAX_ORDER_EMAIL_ATTEMPTS`), `attempts`, `next_attempt_at`, `last_error` and `sent_at`. Type, locale and status are limited by CHECK constraints, so a new email type is a migration that rewrites the check. Rows cascade with their order. `claimOrderEmails` (`db/queries/order-emails.ts`) is a lease: one `UPDATE … WHERE id IN (… FOR UPDATE SKIP LOCKED)` that counts the attempt and moves `next_attempt_at` to the retry time (`ORDER_EMAIL_RETRY_DELAYS_MINUTES`), so concurrent senders never share a row and a crash mid-send means a later retry. Delivery is at least once.
- `carts.updated_at` and `orders.updated_at` are refreshed by Drizzle's `$onUpdate` on every query-builder update. Raw SQL updates must set `updated_at = now()` themselves, and changes to `cart_items` must bump their cart's `updated_at` (the abandoned-cart job relies on it).
- Abandoned carts (#19): `pnpm db:mark-abandoned-carts` (`db/abandoned-carts.ts`, query `markAbandonedCarts`) marks `active` carts with lines and no activity for `ABANDONED_CART_HOURS` (default 24, read from `process.env`, not `getEnv()`) as `abandoned` and sets `carts.abandoned_at`. It deliberately keeps `updated_at` (it sets it to itself, overriding `$onUpdate`), so `updated_at` stays the last activity. Only the job writes `abandoned_at`, and it's an ML feature.
- One active cart per owner: the partial unique indexes `carts_active_user_id_unique` and `carts_active_guest_session_id_unique` (#10) allow a single `active` cart per user and per guest session, so `insertActiveCart` uses `onConflictDoNothing` and re-reads.
- `users.role` (`user_role` enum from `USER_ROLES`: `customer` | `admin`, default `customer`) is what `requireAdmin` checks (#14). The in-app `/admin` area is gone (#40), but the role stays for future admin-only endpoints. Change it only with `setUserRole` / `pnpm db:make-admin`.
- `products.active` (#40) is `false` once a product is archived or deleted in Strapi. Every storefront query filters on it (`isListed` in `db/queries/products.ts`), and cart and checkout read stock through `availableStock`, which is 0 for an inactive product, so its lines answer `exceeds-stock` / `insufficient-stock`. Never delete product rows: order history joins them for the title and image. `products.slug` is set from Strapi (unique, `null` until the first sync, which backfills one from the title).
- Product URLs (#83) are `/products/<slug>`. Build every product link with `productHref({ id, slug })` from `~/lib/products` (it falls back to the `public_id` while a product has no slug); never write `/products/${…}` yourself. The route's `:handle` goes through `resolveProductHandle` (`services/products.ts`): a UUID is a `public_id` and answers 301 to the slug URL once there is one, a current slug renders, a former slug in `product_slug_history` answers 301 to the current one (the query string is kept), and anything else, or an archived product, is a 404. Slugs match case-sensitively, and `~/lib/cms-sync` refuses a UUID-shaped slug, which could never be reached.
- `products.updated_at` (#87) uses the shared `updatedAt()` helper, so every query-builder update of a product (each Strapi save via `updateProduct`, archiving) refreshes it; a raw-SQL update must set it itself. Variant price and stock changes don't touch it. It's the product's `lastmod` in `/sitemap.xml`: `listSitemapProducts` lists the listed products with a size and a slug (UUID-only products are left out). The pure XML and robots.txt builders live in `seo/`.
- Fragrance families, notes and the store code (#65): `products.fragrance_families` (`text[]`, primary first, GIN index) holds every family, and `products.fragrance_family` is kept as the primary for the ML models: the CHECK `products_fragrance_family_primary_check` (`fragrance_family is not distinct from fragrance_families[1]`) refuses any write that lets them drift, so set both together (`fragranceFamily: families[0] ?? null`). New values come from `FRAGRANCE_FAMILIES` (`~/lib/enums`, validated in `~/lib/cms-sync`), but rows from before #65 may hold others (e.g. `мікс`), so reads stay `string` and `fragranceFamilyLabel` shows such a value as stored. A single perfume needs a family; a set (`pack_size > 1`) may have none. `products.notes` (`text[]`) is Ukrainian only. `products.store_code` (`varchar(20)`) is staff-only and deliberately not unique: the owner's women's and men's lists reuse codes, and `11-L` is two perfumes (#66). The catalog filter takes a **list** (`ProductFilters.fragranceFamilies`, matched by `familyFilter` with `&&`: any of them), and the filter options unnest every family.
- Popular perfumes (#67): `products.popular_rank` (nullable `integer`, CHECK `> 0`, **not unique**) is the staff order on `/popular`, edited in Strapi as `popularRank` and synced like the other product fields; `null` means not on the list. `listPopularProducts` (`db/queries/products.ts`) orders listed products by `popular_rank` (nulls last), then the bestseller order (`soldUnits`, shared with `listBestsellers`), narrowed by `familyFilter` and `genderFilter` (every gender when none is given). `getPopularPage(filter, page)` (`services/products.ts`) maps the trio builder's `gender` (#102) through `GENDER_SCOPE`, so unisex perfumes count for both, like the catalogs. It shows every ranked product, 12 per page, and tops the list up with unranked bestsellers only to fill the first page, so it never grows into the whole catalog.
- `orders.shipped_at` and `orders.completed_at` (#40) are set with the status, like `paid_at` / `cancelled_at` / `refunded_at`. Together with `created_at` they are delivery-time features for the LTV/churn models: never drop or rename them.
- CMS outbox (`cms_outbox`, #40): one row per `entity` (`CMS_SYNC_ENTITIES`: `order` | `product`) and `entity_id`, queued with `enqueueCmsSync(tx, …)` in the transaction that changed the order or the product's stock. Queuing again bumps `version`; `markCmsSynced` / `markCmsSyncFailed` only touch the version they claimed, so a push that raced a newer change leaves the row due. `claimCmsSync` is the same `FOR UPDATE SKIP LOCKED` lease as `claimOrderEmails`, and rows are retried forever (`CMS_SYNC_RETRY_DELAYS_MINUTES`, the last delay repeats).
- Migrations: `pnpm db:generate --name <name>` writes them to `db/migrations/`. Every migration needs a hand-written reverse in `db/rollbacks/<tag>.sql`, which `pnpm db:rollback` (`rollbackLatest` in `db/migrator.ts`) runs. Never edit an applied migration.
- `pnpm db:seed` (`db/seed.ts`) inserts `SAMPLE_PRODUCTS` from `db/seed-data.ts` with `onConflictDoNothing` on `public_id`, then their `variants` with `onConflictDoNothing` on `(product_id, volume_ml)`, so new sample sizes reach existing databases. It only loads the small sample catalog; the owner's real range comes from `pnpm db:import-catalog` (below; #66 replaced the seeded copy #67 added). Give new sample products a fresh fixed UUID v7, and never change an existing one.
- Sizes: `PERFUME_VOLUMES_ML` is 5, 10, 30, 50 and 100 ml; 7 ml was dropped in #66 (migration 0015 deleted those sizes, and order lines keep their `volume_ml = 7` snapshot).
- The shop's range (#66): `db/catalog-data.ts` (`CATALOG_PRODUCTS`) is **generated** by `pnpm db:convert-catalog <owner's list>` from the owner's Markdown list (not committed) through `db/catalog/parse.ts` and the owner-approved corrections in `db/catalog/fixes.ts`; fix those and convert again instead of editing the data file. Each entry's `publicId` is `catalogPublicId(list, code, title as written)`, a name-based UUID, so renames in `fixes.ts` or in Strapi never create a copy. `pnpm db:import-catalog` (`importCatalog` in `db/import-catalog.ts`) inserts the entries that aren't there yet with every size of `CATALOG_PRICES` (`db/catalog-prices.ts`) untracked (#98), and queues them in `cms_outbox`, in one transaction. For an existing product it only fills a description that is empty (below); everything else staff changed survives a re-run. The owner's `(popular)` marker becomes `popularRank` 1–30 in list order (women first), stored as `products.popular_rank` on the products the import inserts.
- Descriptions (#100): `products.description` is the Ukrainian text and `products.description_en` the English one, both plain text with a blank line between paragraphs, at most `MAX_PRODUCT_DESCRIPTION` (5000) characters through the Strapi sync. The product page picks the URL's language with `pickDescription` (`~/lib/products`), falling back to the other language, and `ProductDetail.descriptionLocale` says which one it served (mark a fallback with `useContentLang`). The catalog's texts are hand-written in `db/catalog-descriptions.ts` (`CATALOG_DESCRIPTIONS`, `{ uk, en }` by `publicId`, not generated; `catalog-descriptions.test.ts` checks every perfume has one within the limits). `importCatalog` inserts them with new products, and `fillEmptyDescriptions` (`db/queries/products.ts`) gives existing ones only the languages that are `null` or blank, queuing those products for Strapi. It never changes text that's there, so staff edits in Strapi always win.
- Standard sizes and prices (#98): `pnpm db:apply-catalog-prices` (`applyCatalogPrices` in `db/apply-catalog-prices.ts`) is a one-off fix in one transaction. It archives every active set (`pack_size > 1`, so none undercuts the tester trio), gives every active product each size of `CATALOG_PRICES` it lacks (untracked), sets every price to the table, deletes sizes outside it, sets the deprecated product columns from the smallest size, and queues the changed products. Each write matches only rows that differ, so a second run changes nothing (not even `updated_at`). It never changes `track_stock`. A run after staff changed prices in Strapi resets them, so don't schedule it.
- `pnpm db:seed` inserts the sample sizes **tracked** (`track_stock = true`), because the samples are the fixtures for sold-out and low-stock sizes. The sample 3 × 10 ml tester set is seeded archived (#98).
- Put query functions in `db/queries/<area>.ts` and keep them small and typed. Put business rules that combine several queries in `services/`.
- Use `db.transaction(async (tx) => …)` whenever multiple writes must succeed together, and pass `tx` down instead of `db`.
- Raw `db.execute(sql\`…\`)` returns `timestamptz` values as **strings**, so convert them with `new Date()`. Typed queries built with the query builder return `Date`s.

## Visitor and events: `analytics.ts`, `analytics-middleware.ts`, `consent.ts`

- **Consent first.** Nothing is tracked until the visitor clicks "Accept" in the cookie banner: `isTrackingAllowed(request)` is `getConsent(request) === "granted"` and not a bot (`isbot`). The `cookie_consent` cookie (`consent.ts`, env-free) is set by `routes/consent.ts`, which also takes `reset` (the footer's and privacy page's "Cookie settings"). The guest cart's `anonymous_id` and `analytics_session` cookies are strictly necessary and are set without consent, but such a session stores no source, device or landing page.
- The `_shop` layout's `visitorMiddleware` calls `getVisitor` for every request once tracking is allowed, puts the visitor in `visitorContext`, records `page_view` for full page loads (`isDocumentRequest`) and, after the response is built, appends the visitor's `Set-Cookie` headers (and `Cache-Control: private, no-store`). Routes never send the visitor cookies themselves. Resource routes outside the layout (`/cms/*`, `/payments/*`) aren't tracked.
- `getVisitor(request, db, { track })` keeps or creates the `anonymous_id` (1 year) and the session: a new one after `SESSION_TIMEOUT_MINUTES` (30) without a request (checked and touched in one `UPDATE` by `touchActiveSession`), when another `utm_source` arrives, or when a session started without consent can now be tracked. New tracked sessions get `traffic_*` from `resolveTrafficAttribution` (`utm_*`, else the external referrer as `referral`, else `direct` / `none`), `device_type` from `resolveDeviceType`, `landing_page` and the user.
- Actions that need a session even without consent (adding to the cart) call `ensureVisitor({ request, context })`, which reuses or fills `visitorContext`. `readVisitor(request)` only parses the cookies.
- Record an event with `void trackEvent({ request, context }, type, { productId?, properties?, userId? })` from a loader or action under `_shop`. It no-ops without a visitor or consent and never throws, so don't await it unless the test needs to. Each row gets the session's `traffic_*` as `source` / `medium` / `campaign`, and its own request's device and `Referer`. Today: `page_view` (middleware, `/api/events`, `/consent`), `product_view`, `search`, `add_to_cart` / `remove_from_cart` (cart action; the stepper's +/− with `source: "stepper"`) and `login`. **Checkout (#11)** records `checkout_start` from its loader (`subtotal`, `itemCount`, `discountAmount`, `discountCode`) and, after the order transaction commits, `purchase` (`orderId`, `subtotal`, `totalAmount`, `discountAmount`, `discountId`, `discountCode`, `paymentMethod`).
- Loaders that record a view (`product.tsx`, `catalog.tsx`) export `shouldRevalidate = shouldRevalidateView` from `~/lib/analytics`, so a form post elsewhere doesn't record the view again.
- `routes/api.events.ts` takes beacons from the client tracker (`features/analytics`), which sends `page_view` for client-side navigations. It only accepts `CLIENT_EVENT_TYPES` (`page_view`), at most `MAX_CLIENT_EVENTS` per batch and 16 KB, rate-limited per IP, and always answers 204 when it gets that far.
- `linkVisitorToUser(anonymousId, userId)` gives the visitor's userless sessions and events to the user and fills `users.first_touch_*` from their earliest tracked session if they're still empty.
- The cookie names live in `visitor-cookie.ts` (env-free). `hasSessionCookie` also counts `anonymous_id` and `cookie_consent`, so blog pages that show a guest's cart count or no banner aren't cached publicly. Every cookie is listed in `COOKIE_INVENTORY` (`~/lib/consent`) for the privacy page; a test fails when one is missing.

## Cart: `services/cart.ts`

- A user's active cart is found by `user_id`; a guest's by `anonymous_id`, through any of their `sessions` (so it survives a new session), with `user_id` null.
- Loaders read through `getCartOwner(request)` (a stale user cookie counts as a guest) and `getCartView` / `getCartCount`. Writes take a `CartWriter` with the ids from `ensureVisitor`. Only `addItem` may create the cart (`getOrCreateActiveCart`).
- Every change runs in a transaction that locks the cart row (`lockCart`) and ends with `touchCart`. `lockCart` returns whether the cart is still `active`, because the abandoned-cart job may mark it between the lookup and the lock: `addItem` then retries with a new cart, and `updateQuantity` / `removeItem` answer `not-in-cart`.
- `abandoned` is final: the lookups only see `active` carts, so a returning shopper's abandoned cart is gone from `/cart` and their next add creates a new cart. A line's quantity may never exceed its variant's stock (`availableStock`, which is `UNTRACKED_STOCK` for a size that doesn't track stock, #98); stock isn't reserved, so checkout (#11) checks again.
- `mergeGuestCart` runs from `onUserAuthenticated`: without a user cart the guest cart is adopted; otherwise its lines are added to the user's (capped at stock, sold-out sizes dropped) and the guest cart is deleted.
- Line totals and the subtotal are computed in SQL as `numeric`, never in JS. The discount and the total come from `priceCart` (below), which works in whole kopiyky.
- The applied promo code is `carts.discount_id` (`applyPromoCode` / `removePromoCode`, cart intents `apply-promo` / `remove-promo`). It's stored only when it applies to the cart at that moment; afterwards it stays until removed, and `getCartView` says whether it's `applied`, `not-best`, `not-applicable`, `expired`, `used-up` or `invalid`. Refused codes count against `promoCodeLimiter` (10 per client per 15 minutes). `mergeGuestCart` brings the guest's code along unless the user's cart has one.

## Orders: `services/orders.ts`

- `createOrder` (#11) turns the active cart into an order in one transaction: `lockCart`, then the cart's variant rows `FOR UPDATE` in id order (`lockCartLinesForOrder`, so concurrent checkouts can't deadlock or oversell), a stock check before any write, then the order, its lines (`price_at_purchase`, `variant_id`, `volume_ml`), the stock decrement and `carts.status = 'converted'`. User mistakes come back as results (`cart-empty`, `insufficient-stock`); anything thrown rolls everything back.
- `orders.cart_id` is unique: a cart becomes at most one order, and a second submit of the same cart returns the order the first one created.
- Amounts are computed in SQL as `numeric`, from the subtotal and the discount `priceCart` worked out on the locked variant prices, minus what a gift card pays (#125): `total_amount` is what is left to pay, so the order's full price is `total_amount + gift_card_amount` (use that for revenue). Delivery is free when `subtotal − discount` reaches `FREE_SHIPPING_THRESHOLD` (`~/lib/checkout`, 1500 UAH) and otherwise paid by the recipient to Nova Poshta, so `shipping_amount` is always `0` and `orders.free_shipping` records whether the store pays. `orders.discount_amount` and `orders.discount_id` record the applied rule (#59).
- The checkout form posts `expectedTotal`, the total it showed. When the order would cost more (a code was used up or expired meanwhile, or a price rose), `createOrder` throws inside the transaction, so nothing is written, and returns `total-changed`.
- Payment: `card` and `cod` orders are both created `unpaid` / `pending`. After `createOrder`, the `/checkout` action sends a card order to the provider with `startPayment` (see Payments below). Cash on delivery goes straight to the success page as before.
- Confirmation email (#45): `createOrder` takes the checkout `locale` and queues the `confirmation` row in `order_emails` inside its transaction, so a rolled-back order queues nothing and a double submit (`placed: false`) queues no second one. The `/checkout` action then calls `void deliverOrderConfirmation(orderId)` for a `placed` order, and `pnpm db:send-order-emails` (cron, every 5 minutes) retries failures.
- The success page `/checkout/success/:orderId` shows an order only to its user or to the browser it was placed in (`SessionData.orderIds`, set by `rememberOrder`); everyone else gets a 404.
- #18 adds the `checkout_start` and `purchase` events where `routes/checkout.tsx` has `// #18:` comments.
- Account (#12): `getAccountOrders` / `getAccountOrder` read a user's orders through queries that filter by `orders.user_id` in SQL (`listUserOrders`, `findUserOrder`), so an order that isn't theirs is never loaded and its page answers 404. Guest orders with the same email aren't linked. Lines come from `listOrderLinesByOrderIds` at `price_at_purchase`, in one query for all orders. Which statuses count as current or previous lives in `~/lib/account`. The `account.tsx` layout and every child loader call `requireUser` themselves, since loaders run in parallel.

## CMS sync: `services/cms-sync.ts`, `services/cms-push.ts`, `routes/cms.*` (#40)

PostgreSQL is the system of record for products, stock and orders; the Strapi admin is where staff edit them. Two directions:

- **Strapi → app (write-through).** Strapi's document middleware (`cms/src/sync/middleware.ts`) sends every staff create, update or delete of a `product`, and every `order` update, to `POST /cms/products` or `POST /cms/orders/:id` before Strapi saves it. The routes check `CMS_SYNC_SECRET` (`checkCmsSyncAuth`, constant-time), validate with the zod schemas in `~/lib/cms-sync` and answer 200 with the stored state (Strapi saves exactly that), 422 `{ error, … }` for a refusal (Strapi shows it in Ukrainian), 404 for an unknown order, 400 for a body that isn't JSON.
  - The product's descriptions are two plain `text` fields, `description` (Ukrainian) and `descriptionEn` (#100), since the product type isn't localized. The middleware sends both and saves the app's trimmed answer.
  - Strapi edits a product's families and notes as repeatable components (`catalog.fragrance-family` with an enumeration of the Ukrainian values, `catalog.note`), so the order is kept; the middleware sends plain lists and writes the app's normalised lists back as rows, and `toStrapiProductData` turns them into rows for pushes. Strapi has no `fragranceFamily` field: the app derives it.
  - Each Strapi size (`catalog.variant`) has `trackStock` (boolean, default off, #98). The admin hides `stock` while it's off (`conditions.visible`) and then leaves it out of the saved data, so the middleware sends the stored stock instead. `cmsVariantSchema` defaults a missing `trackStock` to `false`.
  - `applyCmsProductChange`: one transaction. `create` inserts the product and its sizes (the deprecated product columns come from the smallest size) and returns the new `public_id`. A changed slug is kept in `product_slug_history` (`db/queries/product-slugs.ts`, slug as primary key) so old URLs redirect, and the slug a product takes is removed from it, so history never shadows a current slug. `update` locks the product and its variants, matches sizes by `volume_ml`, applies stock as `stock - expectedStock` (clamped at 0) when the size tracks stock before and after the edit, otherwise stores the typed stock (`editedStock`), and deletes removed sizes. `delete` only sets `active = false`. A taken slug is `slug-taken` (from `23505`). The route resolves Strapi's relative `/uploads/…` image URL against `STRAPI_URL`.
  - `applyCmsOrderChange`: locks the order, runs `nextOrderState` (`~/lib/order-status`: the transition table, the timestamps, the restock rule), writes the patch and, for `cancelled` / `unclaimed`, puts each line's units back on its variant (locked in id order, like checkout) and queues those products. A refused change writes nothing. Staff only change `status` and `payment_status`; every other order field Strapi stores comes from the app's answer.
- **App → Strapi (outbox).** `createOrder` queues the order and its products, `handlePaymentCallback` the paid order, `applyCmsOrderChange` the restocked products, all inside their transactions. After the commit the route calls `void pushToCms()`. `deliverCmsSync` (in `cms-push.ts`, which must not import `db/index.ts`) claims due rows and upserts each entity's current state in Strapi with `cmsWrite` (`cms/writer.ts`, `STRAPI_SYNC_TOKEN`), finding the document by `orderId` / `publicId`. It never rejects. The Strapi order stores the status as `orderStatus` (Strapi reserves `status`) and amounts as numbers; `toStrapiOrderData` / `toStrapiProductData` map them. `pnpm db:sync-cms` retries due rows; `--all` backfills slugs and queues every product and order (the first sync of an existing database).
- **Product images (#88).** Besides `image_url`, a product edit stores the image's `image_width` / `image_height` and Strapi's resized versions in `image_formats` (`ImageFormat[]`, absolute URLs; the middleware reads them from the upload file, `routes/cms.products.ts` resolves them against `STRAPI_URL`). Without an image all four are `null`. Services turn them into a `ResponsiveImage` with `toResponsiveImage` (`~/lib/images`), the `srcset` of `ProductImage`. Products synced before #88 get them from `pnpm db:backfill-product-images` (`services/product-image-backfill.ts`, reading Strapi with `STRAPI_SYNC_TOKEN`).
- Writes with an API token (the app's pushes) and scripts without a request pass the middleware untouched, so pushes never loop. Strapi refuses order create, delete and clone from the admin, and product clone.

## Discounts: `services/pricing.ts`, `db/queries/discounts.ts` (#59)

- Rules live in `discounts`, not in Strapi, so checkout prices inside its transaction and a CMS outage can't change prices. A rule with a `code` (unique whatever its case, stored uppercase) applies only when the shopper entered it; one without a code applies by itself. `kind` is `DISCOUNT_KINDS` (`percent`, `fixed_amount`, `fixed_price_set`, `percent_every_nth`), limited by a CHECK; a new kind is a migration that rewrites `discounts_kind_check` (and the value or min-quantity check when it needs one). Scopes (`scope_volumes_ml`, `scope_product_public_ids`, `scope_pack_size`) are optional, and products are matched by `public_id` so the rules survive #40. Rules are created by the seed (`SAMPLE_DISCOUNTS`) or a migration; there's no admin UI yet. Deactivate a used rule (`active = false`) rather than deleting it: `orders.discount_id` restricts deletes.
- `priceCart(lines, candidates, now)` is pure: whole kopiyky in and out (`toKopiyky` / `fromKopiyky` from `~/lib/money`), one discount per order (the largest saving; ties go to the entered code, then the older rule), never below 0, and never touching shipping. Windows are start-inclusive and end-exclusive; a rule that hasn't started reads as an unknown code. A `fixed_price_set` prices each set of `min_quantity` qualifying units at `value`, dearest units first, at most `max_sets` sets. A `percent_every_nth` (#124) sorts the qualifying units dearest first and takes `value`% off the last unit of each full group of `min_quantity` (with 2: the cheaper bottle of each pair), at most `max_sets` groups, rounded down once.
- The shop has two automatic rules. The tester trio: any three single (`pack_size 1`) 10 ml sizes for 499 ₴, up to three sets per order, for every shopper. The couple offer (`couple-15`, #124): 15% off the cheaper of each pair of single 30, 50 or 100 ml bottles; migration 0022 creates it the same way, and `db/couple-offer.test.ts` checks it against `SAMPLE_DISCOUNTS` and its 15%. Only one applies per order, whichever saves more. Other savings need a promo code. Migration 0021 creates it in every database (`ON CONFLICT (slug) DO NOTHING`, so a seeded or changed rule is kept). `db/tester-trio.test.ts` checks that the migrated rule matches `SAMPLE_DISCOUNTS` and stays cheaper than `minQuantity ×` the 10 ml price in `CATALOG_PRICES`; otherwise `priceCart` would give no saving while the home page still advertised it.
- To change the trio price: add a migration `UPDATE discounts SET value = '<price>' WHERE slug = 'tester-trio'` (and the same value in `SAMPLE_DISCOUNTS`). The home page badge and "How it works" read the rule (`getTesterTrioOffer`). Staff then edit the Strapi texts that state the price by hand: the home page hero headline and subtitle (uk and en) and the tester-trio offer's `priceNote`, summary and body.
- To change the couple-offer percent: a migration `UPDATE discounts SET value = '<percent>' WHERE slug = 'couple-15'`, the same value in `SAMPLE_DISCOUNTS` and `db/couple-offer.test.ts`, the `checkout.discountCouple` copy in `uk.ts`/`en.ts` (the cart, checkout, order page and email label), and by hand the Strapi `couple-offer` texts (`priceNote`, summary, body, uk and en).
- Checkout redeems the applied rule with `redeemDiscount`, a conditional increment of `redemption_count`. It waits for a concurrent checkout of the same rule and matches nothing once `max_redemptions` is reached, and `createOrder` then prices the cart again without that rule. `discounts_redemptions_check` is the backstop. Candidate rules aren't locked up front, so checkouts with the trio in their candidates don't wait for each other.

## Payments: `payments/`, `services/payments.ts` (#44)

- Card orders are paid on a provider's hosted page. Checkout, the callback route and the success page only see the `PaymentProvider` interface (`payments/provider.ts`). `getPaymentProvider(env)` returns the one `PAYMENT_PROVIDER` names, or `null` when it's unset, in which case card payment is unavailable and the checkout action refuses `card`.
- The only provider so far is the local **simulator** (`payments/simulator.ts`, page `routes/payments.simulator.tsx`). It's shaped like LiqPay: base64 JSON `data` plus a `signature`, an HMAC-SHA256 with a key derived from `SESSION_SECRET`. It's development only: `parseEnv` refuses it in production, and its page answers 404 unless it's the configured provider. Its buttons POST signed callbacks over HTTP to `/payments/callback`.
- Each attempt is a `payments` row with the reference `<order id>-<attempt>` (or `G<gift card id>-<attempt>` for a gift card, #125: `payments.order_id` / `gift_card_id`, exactly one is set, `payments_target_check`). `startPayment` locks the order, requires a `card` / `unpaid` / `pending` order (`isPayable`) and, when given a `viewer`, one that `canViewOrder` allows. It copies the order's `total_amount` into the attempt. **Never take an amount from the request.**
- `handlePaymentCallback` is idempotent. It locks the attempt by reference and ignores unknown references, attempts that already succeeded, and amount or currency mismatches. On success it runs `markOrderPaid`, which only updates an order that is still `pending` / `unpaid` (setting `status`, `payment_status` and `paid_at` together). On failure the order stays `unpaid`. `routes/payments.callback.ts` answers 400 for a bad signature or body and 200 for any verified callback.
- The success page shows `getPaymentView` (`paid`, `pending` or `failed`) for card orders. `routes/checkout-pay.ts` (POST) starts a new attempt for its "Pay now" / "Try again" button.
- A real provider is another `PaymentProvider` implementation plus a migration that extends `payments_provider_check`, and probably a `PUBLIC_URL` for the callback (today's URLs come from the request's origin).

## Gift cards: `services/gift-cards.ts`, `db/queries/gift-cards.ts` (#125)

- Cards of 500, 1000 or 2000 ₴ (`GIFT_CARD_AMOUNTS` in `~/lib/gift-cards`, and `gift_cards_initial_amount_check`) are bought on `/podarunkovi-kartky` (`giftCards`; the offers page links there, #126) by card only, never in a cart: a card is its own `gift_cards` row, so gift card sales are never order revenue and no `purchase` event is recorded for them. The action creates a `pending` card (`createGiftCard`) with its code and full `balance`, remembers it in the session (`SessionData.giftCardIds`, like `orderIds`) and starts a payment (`startGiftCardPayment`, the card's stored `initial_amount`). A successful callback runs `activateGiftCard` (only while `pending`: `active`, `activated_at`, `expires_at` = 12 months later, `payment_id`), queues the `gift_card` email (and `gift_card_recipient` when the buyer named a recipient) and the Strapi push, and the callback route sends them after the commit (`deliverGiftCardEmails`). A failed payment leaves the card `pending`; its page (`giftCardSuccess`, `routes/gift-card-success.tsx`) offers "Try again". Only the buyer (their user id or this browser's session) sees that page and the code (`canViewGiftCard`), and `/account` lists the cards a user bought.
- Codes are 16 symbols of Crockford's base 32 from `crypto.randomInt` (80 bits), unique (`gift_cards_code_unique`; a clash retries), stored uppercase without separators and shown as `XXXX-XXXX-XXXX-XXXX`. Normalize every typed code with `normalizeGiftCardCode` (it reads `O` as `0` and `I`/`L` as `1`). Refused codes count against `giftCardCodeLimiter` (10 per client per 15 minutes). `recipient_email` is optional and dropped when it's the buyer's own; the recipient's email shows nothing else the buyer typed.
- At checkout the card is applied like a promo code (`applyGiftCard` / `removeGiftCard`, intents `apply-gift-card` / `remove-gift-card` on `/checkout`, stored as `carts.gift_card_id`; `mergeGuestCart` brings it along). Those intents answer with the new summary (`CheckoutGiftCardResult`) and the route's `shouldRevalidate` skips its loader for them, so `checkout_start` isn't recorded twice. `checkGiftCard(card, now)` says why a card can't pay (`unknown`, `not-active` for a pending card, `expired`, `used-up`).
- `createOrder` locks the cart's card `FOR UPDATE` after the cart and its variants (`lockCartGiftCard`; the same lock order in every checkout), checks it again, takes `min(balance, total after the discount)` (delivery is always 0), compares what is left with `expectedTotal`, and in the same transaction inserts the redemption (`gift_card_redemptions`), lowers the balance (`used_up` at 0) and stores `orders.gift_card_amount`. A second order racing for the same card waits for the lock, sees the lower balance and gets `total-changed`; `gift_cards_balance_check` is the backstop. The gift card never changes `free_shipping` (decided on `subtotal − discount`). An order the card pays in full is `payment_method = 'gift_card'` and placed `paid` (`orders_gift_card_payment_check`: only with `total_amount = 0`); shoppers never pick that method (`SELECTABLE_PAYMENT_METHODS`).
- When an order is `cancelled` or comes back `unclaimed` (`next.restock`), `applyCmsOrderChange` gives each redemption back once (`restoreGiftCardRedemptions`: balance back, `used_up` → `active` unless expired, `reversed_at` set) and queues the cards. `returned` doesn't, like stock.
- Every check compares `expires_at` with `now`, so an expired card can't pay even before `pnpm db:expire-gift-cards` (daily cron; `db/expire-gift-cards.ts`) marks it `expired` and queues it for Strapi.
- Strapi shows gift cards read-only (`api::gift-card.gift-card`, pushed through `cms_outbox` as `gift_card`, keyed by `giftCardId`, status as `giftCardStatus`): the sync middleware refuses every staff create, update, delete and clone.

## Session: `session.ts`

- Cookie session storage (`__jassmin_session`, httpOnly, sameSite lax, secure in production). Use `getSession`, `commitSession` and `destroySession`, and type new fields in `SessionData`.
- `rememberOrder(request, orderId)` / `getSessionOrderIds(request)` keep the last 10 orders placed in this browser (#11), so guests can open their success page. Logging out clears them.
- `createUserSession({ request, userId, redirectTo })` logs a user in (sets `userId`, returns the redirect with `Set-Cookie`), and `logout(request)` destroys the session. `getUserId` only reads the cookie; use `getUser` when you need to know that the user exists.

## Auth: `services/auth.ts`, `password.ts`, `rate-limit.ts`

- Protected loaders and actions call `requireUser(request)`, which throws a redirect to `/login?redirectTo=<current path>` when logged out. Use `getUser(request)` (`null` when logged out) when the page works for both.
- `requireAdmin(request)` (logged out → login redirect, not an admin → 403) is kept for future admin-only endpoints; call it in every such loader **and** action. The in-app admin area was replaced by the Strapi admin in #40. The role comes from the database on every call (`PublicUser.role`), never from the session cookie, so `pnpm db:make-admin <email> [--revoke]` takes effect on the next request.
- Never select or return `users.password_hash` outside `findUserByEmail` / `verifyLogin` and `findUserCredentialsById` (used only by `services/profile.ts` to check the current password). `PublicUser` is the shape the app gets.
- Passwords are hashed with argon2id in `password.ts` (`hashPassword`, `verifyPassword`). Emails are trimmed and lowercased by the zod schemas in `~/lib/auth` before every lookup or insert.
- Pass every redirect target that comes from the request (e.g. `redirectTo`) through `safeRedirect` from `~/lib/auth`.
- `verifyLogin` updates `last_login_at` (a churn-model feature) on every successful login; `registerUser` sets it too.
- Side effects after a login or registration go in `onUserAuthenticated({ request, context }, userId, kind)`: it merges the guest cart (#10), links the visitor's anonymous sessions and events to the user with `linkVisitorToUser` and records the `login` event (`method: "login" | "register"`, #18). It must never make logging in fail, so each part catches and logs its own errors.
- Failed logins are rate-limited (`loginLimiters`: 5 per email, 20 per IP per 15 minutes) in the shared `rate_limits` table, so the counters survive restarts and deploys (#143).

## Profile: `services/profile.ts`

- `/account/profile` (#54) has three forms told apart by a hidden `intent` (`contact` | `email` | `password`), validated with the schemas in `~/lib/auth` (built from the register rules). A blank phone clears `users.phone`.
- `changeEmail` and `changePassword` check the current password first. Wrong ones are counted by `profilePasswordLimiter` (5 per user id per 15 minutes, shared by both forms); the route checks it before verifying anything. A taken email is detected by the unique index (`23505` → `email-taken`), not a pre-check. New passwords are stored only as `hashPassword` output. Other sessions aren't revoked: the cookie session has no server-side store.
- After a real email change the route calls `void notifyEmailChanged(…)`, a plain-text notice to the **old** address in the request's locale, from `CONTACT_FROM`. It's best effort: no outbox or retry, skipped without `SMTP_URL`, and it never rejects.

## Tests

- Unit tests sit next to the code (`*.test.ts`).
- DB integration tests use `describe.skipIf(!hasDatabase)`, import modules dynamically inside the test (so the env is only validated when a DB exists) and close the pool in `afterAll` (`db.$client.end()`).
- Tests that migrate or write data use `createTestDatabase()` from `db/test-utils.ts` (a throwaway database, dropped in `afterAll`), never the development database.
