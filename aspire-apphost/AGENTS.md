# AGENTS.md: aspire-apphost

Aspire TypeScript AppHost. `apphost.mts` branches on `isPublishMode()`: `pnpm aspire run` declares the local development resources below (`addDevelopmentResources`), and `aspire publish` / `aspire do` declare only the production deployment from `production.mts` (#176). No development resource is ever published.

## Production (publish mode, `production.mts`)

One Hetzner server running Docker Compose (`addDockerComposeEnvironment("jassmin")`, no dashboard); see `docs/deploy.md` for the server, the first deploy and operations.

- **Deploy with `pnpm aspire:deploy`** (`aspire do deploy-ssh -o aspire-output`), with `DEPLOY_SSH_TARGET=deploy@<server>` in the environment. **Never `aspire deploy`**: it also runs Aspire's `docker-compose-up-jassmin`, which starts the stack on the local machine. `deploy-ssh` depends on `push` (build and push every image to GHCR) and `prepare-jassmin` (write `aspire-output/.env.Production` with the values); it copies `docker-compose.yaml` with `scp`, pipes the env file over `ssh` into `/srv/jassmin/.env` (`umask 077`) and runs `docker compose pull && up -d --remove-orphans` there. `pnpm aspire publish -o aspire-output` writes only the Compose file and an empty `.env` template. `aspire-output/` is git-ignored.
- **Services:** `postgres` (`postgres:18`, `jassmindb` + `strapidb`, named data volume), `db-migrate` (the `jobs` image: `pnpm db:create-databases jassmindb strapidb && pnpm db:migrate`; Compose's Postgres starts empty, and has no health check here, so `db:create-databases` retries the connection), `cms` (`cms/Dockerfile`, uploads volume, waits for `db-migrate`), `web` (root `Dockerfile` target `web`), `scheduler` (target `jobs`, supercronic with `deploy/crontab`), `pg-backup` (`deploy/pg-backup`, nightly dumps into the host's `/srv/jassmin/backups`) and `proxy` (`deploy/caddy`, the only service with host ports, 80 and 443). Everything restarts `unless-stopped`, except `db-migrate`.
- **Images:** every `addDockerfile` resource is pushed to the `ghcr` registry (`registry-endpoint`, default `ghcr.io`, + `ghcr-repository`); the server pulls them. All Dockerfiles build from the repo root context (`.dockerignore`), except `deploy/caddy` and `deploy/pg-backup`.
- **Parameters:** asked for on the first deploy: `site-domain`, `admin-domain`, `ghcr-repository`, `smtp-url`, `email-webhook-secret`, `strapi-api-token`, `strapi-sync-token`. Generated (`addParameterWithGeneratedValue`, persisted): `postgres-password`, `session-secret`, `cms-sync-secret`, `email-unsubscribe-secret` and Strapi's six secrets. Aspire keeps the values in `~/.aspire/deployments/<hash>/production.json`. Generated values must never change after the first deploy (sessions, unsubscribe links, Strapi's encryption key).
- **Environment:** `web` and `scheduler` get the same app environment (`NODE_ENV=production`, `JASSMINDB_URI`, `PUBLIC_SITE_URL`, `TRUSTED_PROXY_HOPS=1`, `STRAPI_URL=http://cms:1337`, the tokens and email secrets, `NEWSLETTER_DAILY_LIMIT=200`, #181); no `PAYMENT_PROVIDER` and no `AI_*` (#167). A new variable the app needs in production goes in that loop.
- Pipeline steps: inspect them with `pnpm aspire do --list-steps`. A pipeline step can't read a parameter's value in the TypeScript SDK, which is why the SSH target is an environment variable.

## Development (run mode)


- `apphost.mts` names the dashboard "Jassmin" (`createBuilder({ dashboardApplicationName })`) and declares the resources:
  - `postgres`: PostgreSQL container with a persistent data volume.
  - `jassmindb`: the app database on that server.
  - `db-migrate`: child of `jassmindb` that runs `pnpm db:migrate` on every run. `web` waits for it to complete (`waitForCompletion`). It owns the root `pnpm install` (`withPnpm()`), so every other JavaScript resource uses `withPnpm({ install: false })`.
  - `db-seed` / `db-rollback`: explicit-start children of `jassmindb` that run `pnpm db:seed` / `pnpm db:rollback` against the Aspire database, whose password only Aspire knows.
  - `db-import-catalog`: explicit-start child of `jassmindb` that runs `pnpm db:import-catalog` (#66) once, after `db-migrate`: it adds the shop's perfume range that isn't in the database yet and queues it for Strapi, so start `db-sync-cms` afterwards.
  - `db-apply-catalog-prices`: explicit-start child of `jassmindb` that runs `pnpm db:apply-catalog-prices` (#98) once, after `db-migrate`: it archives sets and gives every active perfume the five standard sizes at the standard prices, and queues the changed products for Strapi, so start `db-sync-cms` afterwards. A second run changes nothing.
  - `db-mark-abandoned-carts`: explicit-start child of `jassmindb` that runs `pnpm db:mark-abandoned-carts` (#19) once, after `db-migrate`. In production the job runs hourly from cron instead.
  - `db-cancel-unpaid-orders`: explicit-start child of `jassmindb` that runs `pnpm db:cancel-unpaid-orders` (#128) once, after `db-migrate`: it cancels card orders still unpaid `UNPAID_ORDER_HOURS` (default 48) after checkout, with the reason `payment_failed`, restocks them and queues them for Strapi, so start `db-sync-cms` afterwards. In production the job runs hourly from cron.
  - `db-expire-gift-cards`: explicit-start child of `jassmindb` that runs `pnpm db:expire-gift-cards` (#125) once, after `db-migrate`: it marks active gift cards past their 12 months as `expired` and queues them for Strapi, so start `db-sync-cms` afterwards. In production the job runs daily from cron.
  - `db-prune-rate-limits`: explicit-start child of `jassmindb` that runs `pnpm db:prune-rate-limits` (#143) once, after `db-migrate`: it deletes the `rate_limits` rows whose window has ended. In production the job runs daily from cron.
  - `db-prune-perfumer-chats`: explicit-start child of `jassmindb` that runs `pnpm db:prune-perfumer-chats` (#180) once, after `db-migrate`: it deletes AI perfumer chats not updated for `PERFUMER_CHAT_RETENTION_DAYS` (default 90), deleted ones included. In production the job runs daily from cron.
  - `db-send-order-emails`: explicit-start child of `jassmindb` that runs `pnpm db:send-order-emails` (#45) once, after `db-migrate`, with `SMTP_URL` from `smtp4dev`. It sends queued order emails that are due, e.g. after smtp4dev was down at checkout. In production the job runs every 5 minutes from cron.
  - `db-sync-cms`: explicit-start child of `jassmindb` that runs `pnpm db:sync-cms` (#40) once, after `db-migrate` and once `cms` is up, with `STRAPI_URL` from `cms` (`STRAPI_SYNC_TOKEN` comes from the root `.env`). It pushes queued order and stock changes to Strapi, e.g. after Strapi was down at checkout. In production the job runs every 5 minutes from cron.
  - `db-send-newsletters`: explicit-start child of `jassmindb` that runs `pnpm db:send-newsletters` (#181) once, after `db-migrate`, with `SMTP_URL` from `smtp4dev` and `STRAPI_URL` from `cms` (`STRAPI_SYNC_TOKEN` from the root `.env`). It sends the queued newsletter emails within `NEWSLETTER_DAILY_LIMIT` and pushes their counts to Strapi. In production the job runs every 15 minutes from cron.
  - `db-backfill-product-images`: explicit-start child of `jassmindb` that runs `pnpm db:backfill-product-images` (#88) once, after `db-migrate` and once `cms` is up, with `STRAPI_URL` from `cms` (`STRAPI_SYNC_TOKEN` from the root `.env`). It copies the size and resized formats of every product's Strapi image into `products`, for products synced before #88.
  - `cms-sync-secret`: a generated, persisted secret parameter (`addParameterWithGeneratedValue`), passed to both `cms` and `web` as `CMS_SYNC_SECRET` (#40). Strapi sends it to the app's `/cms/*` sync routes.
  - `strapidb`: the Strapi CMS database on the same server.
  - `jassmin-synth`: the `jassmin_synth` database for synthetic analytics data (#131); the app never uses it.
  - `synth-generate`: explicit-start child of `jassmin-synth` that runs `uv run analytics/generator/generate.py --load-app-schema` (an `addExecutable`, so `uv` must be on the PATH). It gets the synth database as `JASSMIN_SYNTH_URI` (never `jassmindb`), waits for `db-migrate`'s root install, applies the app's migrations to `jassmin_synth` with `pnpm db:migrate` and loads `raw.*` and `public.*`. See `analytics/README.md`.
  - `dbt-build` / `dbt-docs`: explicit-start children of `jassmin-synth` (#132, `addExecutable`, so `uv` must be on the PATH) that run the dbt warehouse through `uv run --project analytics/warehouse analytics/warehouse/wh.py`: `build` builds and tests raw → staging → marts in `jassmin_synth`, and `docs serve` generates the docs and serves the lineage graph on its `http` endpoint (the port reaches `wh.py` as `WAREHOUSE_DOCS_PORT`). Both get the synth database as `JASSMIN_SYNTH_URI`, and `wh.py` refuses any other database. Start `synth-generate` first. See `analytics/warehouse/README.md`.
  - `ml-notebooks` / `jupyter-lab`: explicit-start children of `jassmin-synth` (#159, `addExecutable`, so `uv` must be on the PATH) for the #133 ML notebooks, through `uv run --project analytics/notebooks`. `ml-notebooks` runs `analytics/notebooks/run_all.py`: all five notebooks headless, saved in place with their outputs; it exits non-zero at the first notebook whose checks fail. `jupyter-lab` serves JupyterLab on its `http` endpoint, bound to `127.0.0.1` only and opened on `analytics/notebooks/`; Jupyter reads the port from `JUPYTER_PORT` (set by the endpoint) and its token from `JUPYTER_TOKEN`, which comes from `jupyter-token`, a generated, persisted secret parameter. Open it with the resource's `JupyterLab` link, which carries the token (the plain endpoint link shows Jupyter's login page). Both get only the synth database as `JASSMIN_SYNTH_URI`, never `jassmindb` or the app's environment, and `jassmin_ml/db.py` refuses any other database and reads read-only. Neither waits for the warehouse: start `synth-generate`, then `dbt-build`, then `ml-notebooks`. Don't run `ml-notebooks` while editing the notebooks in `jupyter-lab`, since both save the same `.ipynb` files. See `analytics/notebooks/README.md`.
  - `cms`: Strapi (`addJavaScriptApp("cms", "../cms", { runScriptName: "develop" })`) on port 1337. It gets `DATABASE_URL` from `strapidb.uriExpression()`, waits for `strapidb` and is health-checked on `/_health`. `withPnpm({ install: false })` is used because the root install run for `db-migrate` already installs the `cms` workspace package. Strapi's secrets come from `cms/.env`. It also gets `CMS_SYNC_SECRET` and, set after `web` is declared, `JASSMIN_APP_URL` from `web`'s `http` endpoint, because product and order edits in the Strapi admin write through to the app (#40). `cms` doesn't wait for `web` (that would be a cycle), so such an edit fails with a clear message while the app is down.
  - `cms-seed`: explicit-start child of `cms` that runs `pnpm seed --token` against `strapidb` (whose password only Aspire knows) and prints the app's API token in its logs.
  - `smtp4dev`: fake SMTP server container (`rnwood/smtp4dev:v3`) for local email. Its `smtp` endpoint (container port 25) is passed to `web` as `SMTP_URL`; its `http` endpoint is the web UI that shows every caught message (open it from the dashboard).
  - `web`: the React Router dev server (`addViteApp("web", "..")`, run with pnpm, `install: false`). It has a reference to `jassmindb` (injected as `JASSMINDB_URI`), waits until the database is healthy and until `db-migrate` has completed. It also references `cms` and gets its endpoint as `STRAPI_URL`, but deliberately doesn't wait for it: CMS outages show up as 503s on CMS pages instead of blocking the shop. It gets `SMTP_URL` from `smtp4dev` and doesn't wait for it either, and `CMS_SYNC_SECRET` from `cms-sync-secret`. The AI perfumer's `AI_BASE_URL`, `AI_MODEL`, `AI_TIMEOUT_MS` and `AI_KEEP_ALIVE` (#162) are forwarded only when set in the AppHost's environment, so the perfumer stays off for anyone without Ollama; there's no Ollama container (run it natively, see `docs/ai-perfumer.md`). `AI_API_KEY` is never forwarded: `web` reads it from the root `.env`, so it doesn't show in the dashboard.
- `.aspire/modules/` is the **generated** SDK. Don't edit or commit it; it's regenerated by `aspire restore` / `aspire add`. Read its typings to find the exact API (e.g. `addPostgres`, `withDataVolume`, `addViteApp`, `withPnpm`).
- Add integrations with `aspire add <name>` (e.g. `aspire add redis`). The package versions are recorded in the root `aspire.config.json`.
- **One Aspire version everywhere (17.0.0, #184):** `sdk.version`, every `packages` entry in `aspire.config.json`, and the CLI version in the README prerequisites must match. Never commit an `aspire.config.json` change that comes only from a CLI update prompt. Upgrade in its own issue and PR, the CLI first (`aspire update --self --channel stable`), then `pnpm aspire update`. See `docs/setup.md` → Upgrading Aspire.
- Since 17.0, the AppHost's secrets (the persisted generated parameters: `postgres-password`, `cms-sync-secret`, `jupyter-token`) live in `~/.aspire/secrets/<apphost-id>/<environment>.json`, not in .NET user secrets (imported on the first 17.0 run). Inspect them with `aspire secret list` / `aspire secret path`.
- This is a **standalone pnpm package with its own lockfile**, not a member of the root workspace. Aspire installs it with `pnpm install --ignore-workspace`, which ignores every `pnpm-workspace.yaml`.
- For the same reason, always start Aspire with **`pnpm aspire <cmd>`** from the repo root. `scripts/aspire.mjs` sets `pnpm_config_allow_builds` so pnpm 12 accepts esbuild's build script, which comes in through `tsx`. That variable also overrides `allowBuilds` for the root install Aspire runs for `db-migrate`, so it lists the Strapi entries (`@swc/core`, `core-js-pure`) as well. Keep it in sync with `pnpm-workspace.yaml`.
- `tsconfig.apphost.json` needs `"types": ["node"]`, because TypeScript 7 no longer auto-includes `@types`.
- Check your changes with `pnpm aspire:build` from the repo root (`tsc -p tsconfig.apphost.json`). Biome lints `apphost.mts` together with the rest of the repo.
- If Aspire fails with DCP/TLS errors ("The SSL connection could not be established", "container volumes did not become ready"), run `aspire doctor`. HTTPS-scanning antivirus software (e.g. Avast Web Shield) can block DCP's local TLS.
