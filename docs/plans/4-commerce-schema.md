# Plan: Create commerce schema: carts, cart_items, orders and order_items (#4)

Issue: https://github.com/savchukolgaa/jassmin/issues/4
Branch: `issue/4`
Worktree: `../jassmin-worktrees/issue-4`
Status: Planned

## Goal
As a store owner, I want carts and orders stored with full financial and lifecycle detail, so I can fulfil orders reliably and later analyse revenue, profit and customer lifetime value. This issue adds a Drizzle migration for `carts`, `cart_items`, `orders` and `order_items`, with the financial breakdown and lifecycle timestamps, plus shared TS types for all four entities.

## Dependencies & prerequisites
- **#3 (closed, merged in c1c4f83):** `users`, `products` and the enums `order_status_type`, `payment_status_type` and `cart_status_type` already exist in `app/.server/db/schema.ts` and migration `0000_core_schema`. The enum value arrays live in `app/lib/enums.ts`.
- **#5 (open, not in code):** `sessions` doesn't exist yet, so `carts.session_id` can't have its FK in this migration. #5 already says "If not done in #4, add FK `carts.session_id → sessions.session_id`", so #5 adds it.
- No new packages or env vars. A PostgreSQL 18+ database is needed for the integration tests (they're skipped without one).
- Downstream consumers: #10 (cart service), #11 (checkout transaction) and #19 (abandoned-cart job, raw SQL on `carts.status` / `updated_at`).

## Decisions & assumptions
- **Primary keys:** `serial` for all four tables, matching `users` and `products`. A `public_id` (UUID v7) for orders is left to #11, which can decide how guests reference their order.
- **Money:** all amount columns are `numeric(10, 2)`, like `products.price`, and come back as strings (`app/.server/AGENTS.md`). `subtotal`, `total_amount` and `price_at_purchase` are not null. `discount_amount` and `shipping_amount` are not null with default `0`. CHECK constraints keep every amount `>= 0`.
- **`carts.session_id`:** a nullable `uuid` column with no FK for now (`sessions.session_id` will be a uuid PK in #5). The FK and its rollback are added in #5.
- **`payment_method`:** stays `text`, as the issue says, but is **not null**, with no default, and has a CHECK constraint `in ('card', 'cod')`. A shared `PAYMENT_METHODS = ["card", "cod"] as const` with a `PaymentMethod` type goes in `app/lib/enums.ts`, and the check is built from that array so the two can't drift. Checkout (#11) always supplies a method.
- **Delete behaviour for user FKs (the issue only specifies product FKs):** `orders.user_id` and `carts.user_id` use **on delete restrict**, so an order or cart never loses its `user_id` and the user's history stays linked for LTV and churn analysis. To delete a user who has carts or orders, a later feature anonymises the account instead (out of scope).
- **Product FKs, as the issue specifies:** `cart_items.product_id` cascades on delete. `order_items.product_id` is nullable and set to null on delete. `cart_items.cart_id` and `order_items.order_id` cascade.
- **Quantities:** `cart_items.quantity` is not null, defaults to 1 and has a check `> 0`. `order_items.quantity` is not null and also gets a check `> 0`, which isn't in the spec but is the natural invariant.
- **Timestamps:** every `created_at`, `updated_at` and `added_at` is `timestamptz not null default now()`. `paid_at`, `cancelled_at` and `refunded_at` are nullable `timestamptz`.
- **Keeping `updated_at` current:** this is done in the service layer with Drizzle's `.$onUpdate(() => new Date())` on `carts.updatedAt` and `orders.updatedAt`, so every query-builder update sets it. The migration stays fully generated by drizzle-kit, which doesn't model triggers. Raw SQL updates set it explicitly, as #19's query already does, and #10's cart service bumps `carts.updated_at` when it changes `cart_items` (that's in #10's spec).
- **Indexes:**
  - required: `orders_guest_email_idx` and `orders_guest_phone_idx`
  - for FK lookups: `orders_user_id_idx`, `order_items_order_id_idx`, `carts_user_id_idx` and `carts_session_id_idx`. `cart_items(cart_id)` is already covered by the unique `(cart_id, product_id)` index.
  - for #19's job: `carts_status_updated_at_idx` on `(status, updated_at)`
  - Constraint and index names are explicit snake_case, per `app/.server/AGENTS.md`.
- **Shared types:** a new isomorphic `app/lib/commerce.ts` exports `Cart`, `CartItem`, `Order` and `OrderItem` interfaces: plain data, money as `string`, timestamps as `Date`, and enum fields typed with the unions from `~/lib/enums`. They're written by hand rather than derived from the schema, because `app/lib/` must not import `app/.server/`. A type-level test keeps them in sync with `$inferSelect`.

## Resolved questions
- **Should `updated_at` use a DB trigger or `$onUpdate`?** `$onUpdate` in the schema; raw SQL sets `updated_at` explicitly (source: answered by the store owner).
- **What happens to carts and orders when a user is deleted?** They keep their `user_id`: the FKs use `on delete restrict` (source: answered by the store owner).
- **Is `payment_method` required?** Yes: not null, with a check limiting it to `card` / `cod` (source: answered by the store owner).
- **Should the `sessions` FK be added here or in #5?** In #5: `sessions` doesn't exist on `origin/main`, and #5's Technical section already covers adding the FK (source: #5, `app/.server/db/schema.ts`).
- **What type should money use?** `numeric(10, 2)`, returned as strings, never floats (source: `app/.server/AGENTS.md`, `products.price`).
- **How are migrations created and rolled back?** With `pnpm db:generate --name commerce_schema`, plus a hand-written `app/.server/db/rollbacks/0001_commerce_schema.sql` that `rollbackLatest` runs (source: `app/.server/AGENTS.md`, `app/.server/db/migrator.ts`).
- **Where are the enums defined?** The values are in `app/lib/enums.ts`, and `cart_status_type`, `order_status_type` and `payment_status_type` already exist in the database from `0000_core_schema` (source: `app/.server/db/migrations/0000_core_schema.sql`).
- **Which cart statuses does analytics need?** `active`, `converted` and `abandoned`. #19 queries `status = 'active' and updated_at < …` with `EXISTS (cart_items)`, so a `(status, updated_at)` index helps (source: #19).
- **How are DB integration tests written?** With `describe.skipIf(!hasDatabase)`, dynamic imports and `createTestDatabase()` from `db/test-utils.ts` (source: `app/.server/AGENTS.md`, `app/.server/db/migrator.test.ts`).

## Steps
Each step is small, ordered, and leaves the app in a working state.

- [x] **1. Shared payment-method values.** In `app/lib/enums.ts`, add `export const PAYMENT_METHODS = ["card", "cod"] as const;` and `export type PaymentMethod = …`, and extend `enums.test.ts`. Check: `pnpm test app/lib`.
- [ ] **2. Commerce tables in `schema.ts`.** Update the header comment, then add:
  - `carts`: `id` serial PK; `userId` integer → `users.id` (`onDelete: "restrict"`); `sessionId` uuid (nullable, with a comment saying the FK comes in #5); `status` `cartStatusType().notNull().default("active")`; `createdAt`; `updatedAt` with `.defaultNow().notNull().$onUpdate(() => new Date())`. Indexes: `carts_user_id_idx`, `carts_session_id_idx`, `carts_status_updated_at_idx`.
  - `cartItems`: `id` serial PK; `cartId` → `carts.id` cascade, not null; `productId` → `products.id` cascade, not null; `quantity` integer not null, default 1; `addedAt` not null, default now. `unique("cart_items_cart_id_product_id_unique").on(t.cartId, t.productId)` and `check("cart_items_quantity_check", sql\`${t.quantity} > 0\`)`.
  - `orders`: `id` serial PK; `userId` → `users.id` restrict; `guestFullName` varchar(255), `guestEmail` varchar(255) and `guestPhone` varchar(50), all not null (lengths match `users`); `shippingAddress` text not null; `status` `orderStatusType` not null, default `pending`; `paymentStatus` `paymentStatusType` not null, default `unpaid`; `paymentMethod` text not null, typed `.$type<PaymentMethod>()`; `subtotal` and `totalAmount` numeric(10,2) not null; `discountAmount` and `shippingAmount` numeric(10,2) not null, default `"0"`; `currency` text not null, default `"UAH"`; `createdAt`; `updatedAt` (with `$onUpdate`); `paidAt`, `cancelledAt`, `refundedAt` nullable. Checks: `orders_payment_method_check` (built from `PAYMENT_METHODS` with `sql.join`), and `orders_amounts_check` (all four amounts `>= 0`). Indexes: `orders_guest_email_idx`, `orders_guest_phone_idx`, `orders_user_id_idx`.
  - `orderItems`: `id` serial PK; `orderId` → `orders.id` cascade, not null; `productId` → `products.id` set null, nullable; `quantity` integer not null; `priceAtPurchase` numeric(10,2) not null. Checks: `order_items_quantity_check` (`> 0`) and `order_items_price_at_purchase_check` (`>= 0`). Index `order_items_order_id_idx`.
  - Check: `pnpm typecheck`.
- [ ] **3. Generate the migration and write its rollback.** Run `pnpm db:generate --name commerce_schema`, then review the SQL: snake_case names, `ON DELETE` clauses, defaults, and no changes to `0000`. Write `rollbacks/0001_commerce_schema.sql`, which drops `order_items`, `orders`, `cart_items` and `carts` in that order, separated by `--> statement-breakpoint`. It doesn't drop any types, because the enums belong to `0000`. Check: `pnpm db:migrate`, then `pnpm db:rollback`, then `pnpm db:migrate` against a dev database.
- [ ] **4. Shared TS types.** Create `app/lib/commerce.ts` with a header comment in the style of `lib/cms.ts`, and add the interfaces `Cart`, `CartItem`, `Order` and `OrderItem`. Fields are camelCase and match the schema: money fields are `string`, timestamps `Date` or `Date | null`, `status: CartStatus | OrderStatus`, `paymentStatus: PaymentStatus`, `paymentMethod: PaymentMethod`, `sessionId: string | null`, `productId: number | null` on `OrderItem`. Check: `pnpm typecheck`.
- [ ] **5. Unit tests in `schema.test.ts`.** Using the existing `describeColumns` helper, test the columns of all four tables. Also test:
  - the check, unique and index names (via `getTableConfig`)
  - the foreign-key `onDelete` actions (`getTableConfig(t).foreignKeys` → `reference().foreignTable` / `onDelete`)
  - `expectTypeOf<typeof carts.$inferSelect>().toEqualTypeOf<Cart>()` and the same for the other three tables

  Check: `pnpm test`.
- [ ] **6. Integration tests in `migrator.test.ts`.**
  - `listTables()` returns `["cart_items", "carts", "order_items", "orders", "products", "users"]`.
  - Defaults: cart `status = 'active'`; order `status = 'pending'`, `payment_status = 'unpaid'`, `currency = 'UAH'`, discount and shipping `"0.00"`; cart item `quantity = 1`.
  - Constraints: `23514` for quantity 0, a negative amount, or `payment_method = 'cash'`; `23505` for a duplicate `(cart_id, product_id)`; `23502` for a missing guest field or `payment_method`.
  - `guest_email` / `guest_phone` indexes exist in `pg_indexes`.
  - Delete behaviour: deleting a product leaves its `order_items` row with `product_id IS NULL` and deletes its `cart_items`; deleting an order cascades to its items; deleting a cart cascades to its items; deleting a user who has a cart or an order fails with `23503` (foreign_key_violation) and leaves `user_id` unchanged.
  - `$onUpdate`: updating a cart's status through Drizzle advances `updated_at`.
  - The rollback test first expects `0001_commerce_schema` (leaving only `products`, `users`), then `0000_core_schema`, then `null`, then migrates up again to all six tables. The existing constraint query, which is limited to `products`/`users`, keeps passing.

  Check: `pnpm test` with a database configured.
- [ ] **7. Docs.** In `app/.server/AGENTS.md` → Database, note that `updated_at` uses `$onUpdate` (raw SQL must set it), that order amounts are `numeric(10, 2)` strings computed server-side, and that `carts.session_id` gets its FK in #5.
- [ ] **8. Final checks.** Run `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build`.
