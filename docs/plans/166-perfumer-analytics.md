## Goal

The store owner wants to know whether the AI perfumer (#162, #163) is used, how well it answers
and whether its recommendations turn into orders, to decide whether to keep it, improve it or pay
for a better model (#167). Each answer records a `perfumer_message` event (counts, ids, timings and
error keys, never text), clicks on its product cards are tagged `list_id: "perfumer"`, customers
can rate an answer 👍/👎 (`perfumer_feedback`), and `docs/ai-perfumer.md` gets the SQL report while
the warehouse gets a `mart_perfumer_daily` mart built on synthetic data.

## Decisions & assumptions

- **`list_id`, not `list`.** The #129 contract's key is `list_id` (`app/lib/analytics.ts`
  `LIST_IDS`); the issue's `list: "perfumer"` means a new `LIST_IDS` value `"perfumer"`.
- **Each perfumer answer is its own list render.** `PerfumerTurn` wraps its picks in a
  `ProductListProvider listId="perfumer" productIds={…}` and passes `listIndex` to `ProductCard`,
  so impressions and clicks get `list_position` 1–4 through the existing tracking
  (`useListedProduct`). No new click code.
- **Attribution.** Perfumer cards have `purchase={false}` (no add-to-cart button), so an order is
  attributed when the same visitor (`anonymous_id`, or `user_id` once known) placed an order within
  7 days of the answer whose `purchase.items` contain a variant of a product that was **recommended**
  (`pick_ids`) — "recommended → ordered" — and separately of a product that was **clicked**
  (`product_click` with `list_id = 'perfumer'`) — "clicked → ordered". Both are in the SQL and mart.
- **Events are recorded on the server, after the answer**, from the route action with
  `void trackEvent(args, "perfumer_message", …)`, so consent (`isTrackingAllowed`) and bot filtering
  apply and the response doesn't wait. The visitor already exists (`ensureVisitor` runs in the
  action). No consent → nothing recorded; the chat works the same.
- **What counts as a "message".** Every request that passes validation records exactly one event:
  answered, failed (engine error), cancelled (aborted) or rate-limited. A request that fails
  `parsePerfumerRequest` (`tooLong`, tampered) records nothing: there's no valid turn.
- **`perfumer_message` properties** (all required; unknown keys rejected, so no text can slip in):
  | Property | Type | Meaning |
  |---|---|---|
  | `reply_id` | uuid | Generated by the server per request; returned to the browser and used by feedback. |
  | `turn` | int 1–100 | The customer's message number in this thread (1 = first). Sent by the browser: the server only sees the last 10 messages, so it can't count. |
  | `latency_ms` | int 0–600 000 | Server time from accepting the message to the result (0 when rate-limited). |
  | `model` | string ≤ 100 \| null | `AI_MODEL` used; `null` when rate-limited before the engine. |
  | `tool_calls` | `{ name, argument_keys: string[] }[]` (≤ 12) | Names (`search_perfumes`, `similar_to`, else `other`) and the argument keys only (`families`, `max_price_uah`, …), never values. Keys are snake_case identifiers ≤ 40 chars, at most 10 per call. |
  | `pick_ids` | uuid[] (≤ 4) | `products.public_id` of the picks shown, in order. |
  | `asked_question` | boolean | The reply has a clarifying question. |
  | `error` | `unavailable` \| `timeout` \| `bad_response` \| `rate_limited` \| `cancelled` \| null | Finer than the chat's error keys (it's for the owner, not the customer): `AiError.kind`, the rate limiter, or `signal.aborted`. |
  | `entry` | `menu` \| `catalog` \| `empty_results` \| `product` \| `corner` \| `direct` | How the conversation was opened. |
- **`perfumer_feedback` properties:** `reply_id` (uuid), `turn` (int 1–100), `rating`
  (`up` \| `down`). Recorded by the same route's action with `intent=feedback` (a separate,
  zod-validated branch), also only with consent. The customer can change their mind; the SQL takes
  the **latest** rating per `reply_id`.
- **`latency_ms` and `model` come from the engine.** `PerfumerTrace` gains `model`; the chat
  service calls `replyWithTrace` instead of `reply` and builds the event properties from the trace.
  The service stays pure: it returns `{ result, event }` and the route records the event.
- **`entry` transport.** The chat page reads `?from=` (validated against `PERFUMER_ENTRIES`, anything
  else → `direct`), stores it with the thread in `sessionStorage` (the entry of the conversation, not
  of each page load; clearing the thread takes the current URL's), and sends it with every message
  as a form field. The header and mobile-menu links (`app/components/layout/nav.ts`) get
  `?from=menu`. `from` isn't a canonical query parameter, so `seoMeta` drops it from the canonical
  URL.
- **Thumbs UI (C+).** Drawn on the C+ canvas (https://claude.ai/artifact/RCvne95y2han2bw8dWm1iW,
  artboards `C+ AI perfumer answer rating (#166)` and its phone version), approved by the owner on
  2026-11-16. Under each perfumer answer that has a `replyId` (answers from before this
  change in `sessionStorage` have none and get no buttons): the label "Відповідь була корисною?" /
  "Was this helpful?" (14 px, 700, `muted`), then a `role="group"` of two 44 px round buttons with
  thumb icons (`aria-label` "Так, корисна" / "Yes, helpful" and "Ні, не допомогла" / "No, not
  helpful", `aria-pressed`): a `line` border and `muted` icon; on hover a `primary` border and a
  slight scale; chosen 👍 fills `primary` with a white icon, chosen 👎 fills `ink` so the two are
  told apart by lightness. After rating, "Дякуємо за відгук!" / "Thanks for your feedback!" with a
  check icon (`success`, `role="status"`, pop-in, reduced motion respected). Pressing the other
  button changes the rating; pressing the chosen one does nothing. Each turn uses its own
  `useFetcher({ key: \`perfumer-feedback-${replyId}\` })` so it never touches the chat fetcher. The
  chosen rating is kept on the thread item (`ThreadItem.rating`), so it survives a reload.
- **Order of work.** The generator (step 9) is done right after steps 1–2: the synthetic contract
  test needs every event type in its fixtures, so the contract and the generator change together.
  The generator draws the perfumer from its own random stream and event-id generator, so every
  other synthetic row keeps its values except where a perfumer visit changes what is viewed.
- **Generator rates (synthetic, plausible):** ~4 % of visits open the perfumer (entries weighted
  menu 40 %, catalog 20 %, empty_results 10 %, product 20 %, corner 10 %), 1–4 messages each; errors
  ~3 % (`timeout` most), rate-limited ~0.5 %; ~70 % of answers with picks (1–4), ~25 % ask a question;
  latency lognormal around 8 s (p95 ≈ 25 s, i.e. a hosted model, not the CPU eval); 15 % of answers
  rated, 75 % up; ~35 % of answers with picks get a card click; visitors who clicked a pick buy it a
  little more often. Exact numbers live in `analytics/generator/config.py`.

## Resolved questions

- **Q3: Thumbs up/down design?** — Approved by the owner on the C+ canvas (2026-11-16), artboards
  `C+ AI perfumer answer rating (#166)` and its phone version.
- **Q1: A server-generated `reply_id` on both events?** — Yes: a uuid per request, returned in the
  action result (`{ ok: true, reply, replyId }`) and sent back with the rating (owner, 2026-11-16).
- **Q2: `corner` and `direct` entries?** — Yes: `menu | catalog | empty_results | product | corner |
  direct` (owner, 2026-11-16).
- **Q4: Record rate-limited requests?** — Yes, as `error: "rate_limited"`; usage counts in the SQL and
  mart exclude them and the error block shows them separately (owner, 2026-11-16).
- **Which key tags perfumer clicks?** — `list_id: "perfumer"` with `list_position`, through
  `ProductListProvider` / `useListedProduct` (source: `app/features/analytics/ProductList.tsx`,
  `docs/analytics-events.md` → Lists).
- **Can the server count the turn?** — No: the browser sends only the last 10 messages
  (`PERFUMER_MAX_MESSAGES`, `toHistory` in `app/lib/perfumer.ts`), so the browser sends `turn`.
- **Where do the model name and tool calls come from?** — `replyWithTrace` → `PerfumerTrace.toolCalls`
  (`app/.server/ai/catalog-tools.ts` `ToolCallRecord`); the model from `getPerfumerConfig()`
  (`app/.server/ai/config.ts`).
- **Server or browser event?** — Server: the action already has the answer, and
  `/api/events` only accepts product events and page views (`toEventInputs` drops anything without a
  product), so the feedback is a route-action branch, as the issue's "feedback action" says.
- **Consent and bots** — `trackEvent` checks `isTrackingAllowed` (`app/.server/analytics.ts`).
- **New event type checklist** — `EVENT_TYPES`, migration + rollback rewriting
  `user_events_event_type_check`, `EventPropertiesMap` + `eventPropertiesSchemas` (kept in sync by
  `satisfies`), the schema test example, the docs (source: `docs/analytics-events.md` → Changing the
  contract; `app/.server/AGENTS.md` → Migrations).
- **Generator fixture rule** — `app/.server/synthetic-data.contract.test.ts` requires every
  `EVENT_TYPES` value (except `review_submit`) in `analytics/generator/fixtures/sample-events.json`
  and validates them against the schemas, so the generator must emit both new events and the
  fixtures must be regenerated (`analytics/README.md` → Development).
- **Warehouse accepted values** — `stg_user_events.event_type` has an `accepted_values` test listing
  every type (`analytics/warehouse/models/staging/_staging__models.yml:320`); it must gain the two
  new types.
- **Text never stored** — enforced by the zod schemas (`.strict()`, only ids / enums / numbers /
  argument keys) and a test that the event built from a reply never contains its intro, reasons or
  question.
