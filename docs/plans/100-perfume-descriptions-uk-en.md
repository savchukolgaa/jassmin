# Plan: Add Ukrainian and English descriptions for every perfume (#100)

Issue: https://github.com/savchukolgaa/jassmin/issues/100
Branch: `issue/100`
Worktree: `.claude/worktrees/issue-100`
Status: Planned

## Goal

Customers choosing a perfume online should read a short description in their own language, so they
know how it smells before they buy a sample. Every product in the owner's catalog
(`CATALOG_PRODUCTS`, 128 perfumes: 75 women's, 53 men's) gets its own hand-written Ukrainian and
English description, based only on its fragrance families and notes. The product page shows the
description in the URL's language. Staff can edit both languages in Strapi, and the import fills
only descriptions that are empty.

## Dependencies & prerequisites

- #66 catalog import (`app/.server/db/catalog-data.ts`, `import-catalog.ts`): on `main`.
- #65 families and notes, #40 Strapi write-through and outbox, #84 locale from the URL
  (`getLocale` reads the path), #85 meta description (`seoMeta` already truncates with
  `truncateDescription`), #86 structured data (`productLd` already uses `product.description`):
  all on `main`.
- New migration `0019_product_description_en` plus `db/rollbacks/0019_product_description_en.sql`.
- No new env vars or packages.
- Deploy order: Strapi's new `descriptionEn` field has to exist before the app pushes it.
  `cmsWrite` sends the whole state, and Strapi rejects unknown fields, so pushes would fail until
  Strapi is updated. The outbox retries them, so nothing is lost, but deploy Strapi first.

## Decisions & assumptions

- **Data model: one new nullable column `products.description_en text`.** `products.description`
  stays and is the Ukrainian text. This is the smallest change. It keeps every existing reader,
  the seed and the ML columns as they are, and avoids a `{ uk, en }` jsonb migration of existing
  data. No column is dropped or renamed.
- **Strapi: a plain `descriptionEn` text field, not i18n.** The `product` type isn't localized,
  and the write-through middleware and `findDocument` by `publicId` assume one document per
  product. Localizing it would create one document per locale and break both. Existing
  `description` stays the Ukrainian field. Admin labels: "Опис (українською)" / "Опис
  (англійською)" through the content-manager field hints in `cms/src/index.ts`, if that mechanism
  covers `api::product.product` (it's keyed by UID). Otherwise set them in the content-manager
  configuration.
- **Content lives in a hand-written data file `app/.server/db/catalog-descriptions.ts`**:
  `CATALOG_DESCRIPTIONS: Readonly<Record<string, { uk: string; en: string }>>`, keyed by
  `publicId`, with a comment naming the perfume above each entry. It's separate from
  `catalog-data.ts` because that file is generated by `pnpm db:convert-catalog` and is overwritten
  on each conversion. `publicId` is stable across renames (name-based UUID), so the keys survive a
  re-conversion.
- **Writing rules** (from the issue): 2–4 sentences, 150–600 characters per language. They
  describe the scent's character and when to wear it, and mention the main notes. Neutral and
  accurate, with no launch years, perfumers, awards, concentrations or "bestseller" claims. The
  English text is a natural rewrite, not a word-for-word translation. Note names in English text
  are translated in prose (e.g. "blackcurrant, pear and iris"), while the stored `notes` stay
  Ukrainian (out of scope). Unisex perfumes (11) are described as suiting anyone.
- **Plain text with paragraphs.** A blank line separates paragraphs. The page splits on
  `/\n\s*\n/` and renders each part as a `<p>`, never as Markdown or HTML. The catalog texts are
  one paragraph each.
- **Import: extend `importCatalog`** (`pnpm db:import-catalog`, already an Aspire resource
  `db-import-catalog`) rather than adding a new script.
  - New products are inserted with both descriptions.
  - Existing products get only the **empty** languages filled, each language on its own: `null`
    or blank (`nullif(btrim(x), '')`). One `UPDATE products … FROM (VALUES …)` sets
    `description = coalesce(nullif(btrim(description), ''), v.uk)`, and the same for
    `description_en`, `WHERE` at least one of them is empty, and sets `updated_at = now()` (raw SQL
    has to, see `app/.server/AGENTS.md`). It returns the ids it changed, which are queued with
    `enqueueCmsSync` in the same transaction.
  - A second run changes nothing and queues nothing.
  - Staff text is never overwritten, including when staff wrote only one language.
- **Locale selection is a pure function in `~/lib/products`**: `pickDescription({ description,
  descriptionEn }, locale)` returns `{ text, locale }`. For `en` it returns `descriptionEn`, and
  falls back to `description` (`locale: "uk"`). For `uk` it returns `description`. It returns
  `null` when both are empty. `ProductDetail` keeps `description: string | null` (the chosen text)
  and gains `descriptionLocale: Locale`, so the page can mark fallback text with
  `lang={useContentLang(…)}` like CMS content.
- `resolveProductHandle(handle, locale, db)` takes the locale (the route passes
  `await getLocale(request)`), and `toDetail` applies `pickDescription`. `meta` and `productLd`
  keep reading `product.description`, so they get the localized text without changes.
- zod: both description fields use one `descriptionText` schema (trimmed, empty means `null`,
  at most `MAX_PRODUCT_DESCRIPTION` = 5000 characters), a sanity cap so a mistaken paste can't
  land in the page and meta. It replaced `optionalText`, whose only user was `description`. The
  Strapi refusal message (`cms/src/utils/app-sync.ts`) names the limit when a description field is
  refused. Strapi's own `description` / `descriptionEn` fields carry the same `maxLength: 5000`,
  so the admin form warns before it saves.

## Resolved questions

- **Does the owner review the 256 texts before they're imported?** Yes, in the PR: the data
  file is grouped women/men with the perfume name above each entry. Fixes after the merge are
  made in Strapi (owner, answering Q1).
- **Is description length capped in the sync schema?** Yes, `.max(5000)` on both fields, with a
  Ukrainian error message in the middleware's refusal (owner, answering Q2).

- **Which language does `products.description` hold?** Ukrainian. The seed's descriptions are
  Ukrainian, and `products.notes` is Ukrainian only (source: `app/.server/db/seed-data.ts`,
  `app/.server/AGENTS.md` → fragrance families).
- **Is the product page's language the URL's or the cookie's?** The URL's: `getLocale(request)`
  reads `localeFromPath` (source: `app/.server/locale.ts:46`, #84).
- **Does the meta description need truncating?** No. `seoMeta` already truncates with
  `truncateDescription` (source: `app/lib/seo.ts:208`).
- **Does structured data need a change?** No new code. `productLd` reads `product.description`,
  which will be the localized text (source: `app/lib/structured-data.ts:170`).
- **Does Strapi save new fields from the app's answer automatically?** For pushes, yes:
  `toStrapiProductData` spreads the whole `CmsProductState` (source:
  `app/.server/services/cms-push.ts:99`). For staff saves, no: `applyProductAnswer`
  (`cms/src/sync/middleware.ts`) copies only chosen fields of the answer, so step 4 also writes
  back the app's trimmed `description` / `descriptionEn` there, next to `productPayload`.
- **New script or extend the import?** Extend it. `db-import-catalog` already exists in Aspire
  (`aspire-apphost/apphost.mts:49`), and the import already queues to `cms_outbox` in one
  transaction.
- **How many products need texts?** 128 (75 women's, 53 men's, 11 of them unisex) (source:
  `app/.server/db/catalog-data.test.ts`).

## Steps

- [x] **1. Schema and migration.** Add `descriptionEn: text()` next to `description` in
  `products` (`db/schema.ts`). Run `pnpm db:generate --name product_description_en`, and write
  `db/rollbacks/0019_product_description_en.sql` (`drop column description_en`). Check that
  `schema.test.ts` and `migrator.test.ts` pass, and that `pnpm db:rollback` and migrate round-trip
  on a dev DB.
- [x] **2. App side of the sync model.** In `~/lib/cms-sync`, add `descriptionEn: optionalText`
  to `productFields` and `descriptionEn: string | null` to `CmsProductState`. In
  `db/queries/products.ts`, add it to `ProductWrite`, `detailColumns` and
  `findProductSyncState`. Map it in `productWrite` (`services/cms-sync.ts`) and
  `toCmsProductState` (`services/cms-push.ts`). Update fixtures and tests (`cms-sync.test.ts`,
  `cms-push.test.ts`, `routes/cms.products.test.ts`) so a create/update with both languages
  stores both and answers both, and a push sends `descriptionEn`.
- [x] **3. Length cap.** Add `.max(5000)` to the description schema used by both fields
  (a separate `descriptionText` so `optionalText`'s other users don't change), with a test. Make
  sure the middleware's 422 shows a Ukrainian message for it.
- [x] **4. Strapi.** Add `"descriptionEn": { "type": "text" }` after `description` in the
  product `schema.json`, and `descriptionEn: text(merged.descriptionEn)` in `productPayload`
  (`cms/src/sync/middleware.ts`), plus a case in its test. Add the admin labels. Regenerate
  `cms/types/generated` (`pnpm --filter jassmin-cms strapi ts:generate-types`). Check it in
  `pnpm cms:dev`: edit both fields, save, and see both columns change in PostgreSQL and the
  answer saved back.
- [ ] **5. Locale on the product page.** Add `pickDescription` and `descriptionLocale` to
  `~/lib/products` (unit tests: `en` with and without English, `uk`, blank strings, both empty).
  Pass `locale` through `resolveProductHandle` → `productResult` → `toDetail`. In
  `routes/product.tsx`, pass `await getLocale(request)`, render the description as
  `text.split(/\n\s*\n/)` paragraphs inside the existing section, and put
  `lang={useContentLang(product.descriptionLocale)}` on the section. Update `product.test.ts`
  (the uk page shows Ukrainian; `/en/` shows English and falls back to Ukrainian with `lang="uk"`;
  the meta description contains the localized text) and `product-jsonld.test.ts`.
- [ ] **6. Write the descriptions: women's list (75).** Create `db/catalog-descriptions.ts`.
  Go through `CATALOG_PRODUCTS` in list order, and for each perfume write `uk` and `en` from its
  `fragranceFamilies` and `notes` only, following the writing rules above. Give each text its
  own opening and structure, so there are no templated sentences. Add
  `catalog-descriptions.test.ts` now, so it guards the work as it grows. Leave the completeness
  assertion as a `todo` until step 7.
- [ ] **7. Write the descriptions: men's list (53),** including the unisex ones. Turn on the
  completeness test:
  - Every `CATALOG_PRODUCTS` `publicId` has an entry, and there are no unknown keys.
  - `uk` and `en` are each 150–600 characters after trimming and have 2–4 sentences.
  - All 256 texts are distinct, and no two products share an opening sentence.
  - No 4-digit years, and none of `парфумер|perfumer|нагород|award|бестселер|bestseller|EDP|EDT`.
  - The `uk` text mentions at least one of the product's notes (a case-insensitive match on the
    note's first 5 letters, so Ukrainian inflection still matches).
  - The `uk` text has Cyrillic, and the `en` text has none.
- [ ] **8. Import fills descriptions.** Change `importCatalog(db, entries, prices,
  descriptions)`:
  - Inserts set `description` / `descriptionEn` from the map.
  - After the insert, `fillEmptyDescriptions(tx, rows)` (in `db/queries/products.ts`): a single
    `UPDATE … FROM (VALUES …)` that fills only empty languages, sets `updated_at = now()` and
    returns ids.
  - Queue the inserted and filled ids together (deduplicated) with `enqueueCmsSync`.
  - Return `descriptionsFilled`.
  - Update the script's output and the docstring ("never touches an existing product" becomes
    "only fills empty descriptions").
  - Integration tests in `import-catalog.test.ts`:
    - A fresh import stores both languages.
    - A product with staff text in `uk` and `null` in `en` gets only `en`.
    - A product with both filled is untouched, with `updated_at` unchanged and not queued.
    - A second run reports 0 filled and queues nothing.
    - Blank `''` counts as empty.
- [ ] **9. Docs.** Update `app/.server/AGENTS.md` (Database: `description_en`, `description` is
  Ukrainian, the import's fill rule; CMS sync: `descriptionEn`) and the `db:import-catalog` row
  and setup step 4 in `README.md`.
- [ ] **10. Verify.** Run `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build`. Then in
  `pnpm aspire run`:
  1. Migrate, then run `db-import-catalog` twice; the second run fills 0.
  2. Run `db-sync-cms`; both fields appear in Strapi.
  3. Open a product at `/…` and `/en/…`: the right language shows, and the `<meta
     name="description">` and JSON-LD match.
  4. Edit the English text in Strapi and see it on the `/en/` page.
  5. Run the import again; the edit survives.

## Out of scope

- Product pictures and availability (separate issues).
- Translating titles, notes or family names (notes stay Ukrainian as stored).
- Descriptions for the sample products in `seed-data.ts` (not part of the owner's catalog), and
  showing descriptions on catalog cards.
- Localizing the Strapi `product` content type.
- Rich text or Markdown in product descriptions.
